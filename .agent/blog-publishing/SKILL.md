# 博客文章与发布

所有路径均相对于本仓库根目录。用户明确说“添加文章”或“发布”时，执行对应流程；只说“添加文章”不触发发布。

## 添加文章

1. 从当前对话获取用户提供的文章标题、主题、日期。缺少哪项就询问哪项，已有信息不重复询问。不得自行根据正文、文件时间或当前日期猜测。
2. 主题写入 `category`，取值为 `风`、`夜晚`、`夏天`、`时间`；日期写成合法的 `YYYY-MM-DD`。主题不在四类中或日期含糊时，先向用户澄清。
3. 在根目录 `list.json` 中添加条目，只使用 `title`、`category`、`date` 三个字段，保持按日期降序排列。`title` 使用用户提供的标题，不带文件扩展名，不改写标题。
4. 在 `passages/` 中新建同名 `标题.md`。用户提供正文时原样写入；未提供正文时创建空文件，不代写内容。如果标题包含无法作为单个文件名的字符，先澄清文件名。
5. 同标题已有索引或文件时，复用已有条目和文件，不生成重复项，不覆盖已有正文；仅更新用户明确提供的元数据或正文修改。
6. 检查 JSON 可解析、字段正确、对应 Markdown 文件存在，然后简要告知新增文件的位置。此步骤不运行 Git 提交或推送。

## 发布

用户明确说“发布”即授权执行本流程，不再额外请求一次发布确认。

1. 在仓库根目录检查 `git status`、当前分支和待发布差异，确认发布目标为 `origin` 的 `master`。若当前不在 `master`，先处理分支归属，不能误把其他分支当作 `master` 发布。
2. 运行 `node build.js`。它会更新索引与正文包 `scripts/content.js` 等生成文件；构建成功后运行 `node scripts/check-content.cjs` 验证索引与文章一致。
3. 根据与 `HEAD` 的差异确定本次新增文章标题。提交说明写清楚“加了什么文章”，例如 `添加文章：文章甲、文章乙`；没有新增文章时，按实际变化写 `更新文章：文章甲` 或 `更新博客`。不要把“加了什么文章”原样当作通用提交说明。
4. 用 `git add -A -- <本次发布涉及的路径>` 暂存文章、对应素材、`list.json`、构建产物，以及当前任务中待发布的站点改动；保留不相关改动原状。随后执行 `git commit -m "添加文章：实际文章标题"`，提交说明按上一步替换。
5. 提交成功后执行 `git push origin master`。没有可提交的差异时不创建空提交，仍可推送 `master` 上已有的待发布提交。
6. 确认推送成功，简要报告提交说明、提交哈希和推送目标。GitHub Pages 部署由推送触发；未核实部署状态时只报告“已推送”，不能声称线上部署已完成。

构建、校验、提交或推送失败时，停在失败步骤并报告实际原因，不继续后续步骤，不强制推送，不重置或丢弃用户改动。处理文章标题等用户文本时使用可靠的参数传递或 shell 引号，避免把标题中的符号当作命令执行。
